# Proposed Methodology

## Overall System Architecture

The proposed system follows a modular NLP pipeline that converts natural-language queries into structured database operations. It consists of data preprocessing, intent classification, entity extraction, query processing, database retrieval, and result presentation.

The pipeline begins with institutional Excel data and natural-language query samples. The data is cleaned and organized, while the query samples are used to develop the intent classification model. At runtime, user queries are processed by the AIML service, and the extracted information is passed to the Next.js backend for database retrieval.

![Proposed System Methodology Pipeline](assets/images/aiml_clg_architecture.jpg){width=5in height=5.4in}

The major stages are:

1. Data collection from institutional Excel files.
2. Data cleaning and preprocessing.
3. Sentence embedding generation and intent classifier training.
4. Named Entity Recognition and USN extraction.
5. Model evaluation and integration.
6. Natural-language query processing through FastAPI.
7. Intent-based database retrieval using Prisma and PostgreSQL.
8. Result presentation through the conversational interface.

## Preprocessing and Feature Engineering

The institutional Excel dataset was cleaned before being imported into PostgreSQL. This involved standardizing column names, correcting inconsistent values, handling missing fields, and removing duplicate records.

For NLP model development, natural-language queries were organized into six intent classes. The query text was processed using the BAAI/bge-small-en-v1.5 sentence-transformer model to generate numerical sentence embeddings.

Each query was represented as a dense vector capturing its semantic meaning. These embeddings were then used as input features for the classification model. The entity extraction component independently processes the original query text.

## Proposed Model

The system combines three techniques to understand user queries.

**Intent Classification**

The BGE-small-en-v1.5 model converts each natural-language query into a sentence embedding. A Logistic Regression classifier predicts the most suitable intent from the generated embedding.

The classifier uses the following Softmax probability model:

$$
P(y = k | x) = softmax(z)_k
$$

Where:

- \(x\) represents the input sentence embedding.
- \(z\) represents the vector of scores generated by the Logistic Regression classifier.
- \(z_k\) represents the score for intent class \(k\).
- \(y\) represents the predicted intent.
- \(k\) represents an individual intent class.
- \(softmax(z)\_k\) represents the predicted probability of class \(k\).

The class with the highest predicted probability is selected as the final intent.

**Named Entity Recognition**

The system uses the RoBERTa-based `Jean-Baptiste/roberta-large-ner-english` model to identify named entities in user queries. The extracted entities are categorized into person and organization types, representing student and company names respectively.

**USN Extraction**

Student USNs are identified separately using regular expressions. The pattern detects identifiers following the institutional USN format.

These three components work together to identify the user's intent, student names, USNs, and company names.

## Training and Model Evaluation

The Logistic Regression classifier is trained using the sentence embeddings generated from the labelled query dataset. The dataset is divided into training, validation, and testing subsets using a 70:15:15 ratio.

The classifier is optimized using the Logistic Regression objective with regularization to reduce overfitting. Model performance is evaluated using accuracy, precision, recall, and F1-score.

The RoBERTa model uses pretrained weights for entity extraction through transfer learning. USN extraction does not require model training because it uses a predefined regular expression.

The selected models are saved and loaded by the AIML service during application execution.

## Implementation

The project uses Python for NLP development and TypeScript for application development.

The AIML service is implemented using:

- Python 3.13 and FastAPI for API development.
- Sentence Transformers for BGE embedding generation.
- Scikit-learn for Logistic Regression classification.
- Hugging Face Transformers for RoBERTa-based entity extraction.
- Uvicorn for running the FastAPI server.
- Joblib for saving and loading the trained classifier.

The web application uses Next.js, React, Prisma ORM, and PostgreSQL.

The implementation follows these steps:

1. Load the trained intent classifier and pretrained NLP models.
2. Receive a natural-language query through the FastAPI endpoint.
3. Generate a sentence embedding and predict the intent.
4. Extract student names and company names using NER.
5. Extract student USNs using regular expressions.
6. Return the predicted intent and extracted entities as JSON.
7. Pass the response to the Next.js backend.
8. Select the appropriate query strategy based on the intent and extracted entities.
9. Execute the corresponding Prisma database query.
10. Return and display the retrieved information in the conversational interface.

## System Integration and Deployment

The system consists of two independently runnable services. The AIML service operates on port 8000, while the Next.js application operates on port 3000.

The Next.js backend communicates with the AIML service through HTTP requests. The AIML service returns structured JSON containing the predicted intent and extracted entities.

The Placement Orchestrator processes this response, cleans extracted values, and selects the appropriate query strategy through the Query Strategy Factory. The selected strategy retrieves information from PostgreSQL using Prisma.

If the AIML service is unavailable, the backend provides keyword-based fallback classification for selected basic queries.

## Privacy, Security and Reliability

The system uses predefined database query strategies instead of generating unrestricted SQL from user input. This provides greater control over database operations and reduces the risk of unintended queries.

Student information is maintained in the institutional database and is used only for the intended academic application. The system also separates NLP processing from database operations, making individual components easier to maintain, test, and update.

Reliability is evaluated through API testing, database result verification, fallback testing, and end-to-end functional testing.
